The problem

The contact center's dialer and CRM is administered through a web interface with no bulk editing for many settings. Adding agents, changing queue delays, updating skills or auditing permissions meant hundreds of clicks, and mistakes were easy to make and hard to spot.

Objective: Let admins read the current state into Excel, edit it there, and push changes back to the platform safely and repeatably.

Step by step

1

Design the suite around read and update pairs

  • Grouped macros by category (Skills, Queues, Permissions, Users, Phone, Campaigns) and named them Category_Action, for example Queues_ReadUserSettings and Queues_UpdateUserSettings.
  • Every update macro has a read macro, so admins always start from the real current state, not from memory.
  • Shared helpers and URL maps are reused across each category to keep behavior consistent.
2

Capture the live page and test logic offline

Testing against the live system is slow and risky. Testing against saved copies of the page is fast and safe.

  • Saved the platform's live HTML for each screen the automation touches.
  • Tested the JavaScript that finds and clicks elements against those captures using Python (BeautifulSoup) and Node.js (jsdom) before writing any VBA.
  • Only then wrote the VBA, which drives Chrome through SeleniumVBA and injects the tested JavaScript.
3

Engineer for a user interface that keeps changing

  • When the vendor moved permissions from a slide-out drawer to an inline component, rewrote that module with name-based toggles and added the new feature and category columns.
  • Only click buttons that are actually visible, so hidden tabs are never triggered by accident.
  • Match results by prefix instead of exact text, because the platform sometimes appends extra details.
  • Narrowed exclusion filters after finding that a broad text match was silently skipping valid records.
' Click only a visible "Save Changes" button, then read the result by prefix Dim js As String, result As String js = "const b=[...document.querySelectorAll('button')]" & _ ".find(x=>x.textContent.trim()==='Save Changes' && x.offsetParent!==null);" & _ "if(!b) return 'NOT FOUND'; b.click(); return 'UPDATED';" result = driver.ExecuteScript(js) If Left(result, 7) = "UPDATED" Then ws.Cells(r, colStatus).Value = "OK" Else ws.Cells(r, colStatus).Value = result End If

Lesson: treat UI automation as fragile

Vendor web apps change without notice. Keep page captures, re-test after every vendor release, and fail loudly instead of guessing.

4

Validate the code structure on every change

  • After each significant edit, checked Sub/Function balance, duplicate names, line-continuation counts and line lengths across the single large module.
  • Kept changes small and re-tested each category on its own.
5

Use the suite for a 7-campaign outbound rollout

Before the annual enrollment period, agents had to call their own existing customers in order of urgency. The dialer could not show the custom field that marked urgency on the call screen.

  • Agreed with the vendor on a workaround: one outbound campaign per urgency value, with the new agent-assignment feature routing each lead only to its owning agent.
  • Transformed the source export into seven upload files and matched each customer's owner to their platform user ID.
  • Produced a review sheet for records that could not be matched, so nobody was dialed by the wrong agent.
  • Audited all seven campaigns afterwards with the Campaigns_ReadAll macro, including lead lists and voicemail settings.

Best practice: audit after every bulk change

A bulk upload is only finished when a read-back confirms the platform holds what you intended.

Outcome

  • Hours of repetitive clicking replaced by spreadsheet-driven updates.
  • Fewer configuration mistakes, because every change starts from a read of the real state.
  • A campaign rollout that worked around a platform limitation without waiting for a vendor feature.
  • Documented patterns that keep the suite working when the vendor changes its interface.
