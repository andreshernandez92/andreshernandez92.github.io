The problem

Callers were waiting too long, some transfers from lead partners failed to connect, and one inbound queue was being starved of calls. Each issue had a different cause, spread across three systems.

Objective: Design routing that always has a next step for the caller, find the real reasons calls fail, and document integrations so anyone on the team can set them up.

Step by step

1

Build the main IVR flow node by node

  • Designed after-hours routing to voicemail, hold sequences with timed milestone messages, and agent bridging.
  • Built and tested each node on its own before connecting the full flow.
2

Add an overflow IVR

  • Built a routing flow that sends callers to the primary team first, then overflows to a second team after a set wait of 60 seconds.
  • Tested on a test queue, then swapped in the live queue at go-live.
  • Documented a platform limitation (the IVR cannot fire webhooks) so nobody designs around a feature that does not exist.
3

Investigate failed transfers

Transfers from lead partners were being billed or offered but not connecting to agents.

  • Cross-referenced the lead marketplace's call logs with the dialer's logs to find where each failed transfer broke.
  • Separated internal terminology from platform terminology, so vendor support and our team were talking about the same setting.
  • Built a tiered ring-group IVR that tries one group of agents, then cascades to the next, and tested it successfully with a colleague.

Lesson: compare logs from both sides

One system says the call was sent, the other says nothing arrived. The answer is almost always in the gap between the two timestamps.

4

Fix a starved queue in VICIdial

  • Found that an overflow in-group had been given a much higher queue priority than everything else, so a standard queue was always served last.
  • Normalized standard in-groups to the same priority while keeping designated overflow groups slightly elevated.
5

Standardize ping integrations with lead partners

  • Documented one standard setup: before a transfer, the marketplace calls a REST endpoint that returns whether the target queue has an available agent.
  • Mapped caller fields (name, phone, state, ZIP, city) and partner tokens to API parameters.
  • Defined case-sensitive response rules: available returns ACCEPT, unavailable returns REJECT.
  • Batched any platform errors into a single message to the vendor instead of many small ones.
GET https://api.<dialer>/availability/byQueue/{queueId} ?first_name={firstName}&last_name={lastName}&phone_number={phone} &state={state}&zip_code={zip}&city={city} Response rule (case sensitive): available == true -> Success -> "ACCEPT" available == false -> Failure -> "REJECT"
6

Document ring trees for raw-call buyers

  • Wrote up the campaign, ring tree and ring tree target hierarchy, and where each buyer's API settings live.
  • Covered call acceptance using JSONPath and JavaScript parsing of the buyer's response, dynamic versus static transfer numbers, revenue rules and ZIP targeting through bulk tags.
  • Kept the whole thing in a living SOP updated every time a new buyer is set up.

Outcome

  • IVR and overflow routing live, so callers always have a next step.
  • A tested tiered ring-group design to raise transfer connection rates.
  • A queue priority fix that ended call starvation for one team.
  • A standard, documented integration setup any team member can follow.
